# Filesystem tools

All file-operation tools that run inside the Nodebox sandbox. The constraint that drives every design choice in this directory: **no npm dependencies.** Nodebox does not allow `npm install`, so the runtime imports only `node:*` builtins. Anything we ship has to be pure JS or built on `node:zlib` / `node:crypto`.

## Archive support (`archive.ts`)

Pure-JS ZIP and TAR parser. Backs both `extract_archive` and `archive_list`.

| Format     | Read | Write | Notes                                                      |
|------------|------|-------|------------------------------------------------------------|
| ZIP store  | ✓    | —     |                                                            |
| ZIP deflate| ✓    | —     | via `node:zlib.inflateRawSync`                             |
| ZIP64      | ✗    | —     | rejected with explicit error                               |
| ZIP encrypt| ✗    | —     |                                                            |
| TAR (ustar)| ✓    | —     |                                                            |
| GZIP       | ✓    | —     | single-stream, auto-detected by magic / extension          |

Safety:
- Path traversal (`..`, absolute paths) blocked.
- `max_files` default **5000**, `max_bytes` default **256 MB**.
- Refusals are reported in `skipped` rather than throwing — partial extractions are useful.

## Document extraction

- **`docx-extract.ts`** — opens the `.docx` ZIP, reads `word/document.xml`, strips tags. Preserves paragraph breaks; tables flatten to lines. No style mapping, no embeds. Good enough for the agent to *read* a Word doc the user sent.
- **`pdf-extract.ts`** — best-effort. Scans `stream`/`endstream` blocks, applies the `/Filter` chain (`FlateDecode`, `ASCII85Decode`, `ASCIIHexDecode`), then extracts `Tj`/`TJ`/`Td` operands. Heuristic to drop streams that look like font-encoded gibberish.
  - **Limits:** custom font encodings (CID maps), encryption, LZW/DCT/JBIG2 filters, object streams (PDF 1.5+). When extraction returns empty / unreadable text, the tool sets `notes` and the agent should surface that to the user.
- **`image-info.ts`** — header-only width/height/format for PNG, JPEG, GIF, WebP (lossy/lossless/extended), BMP. For visual analysis the agent already has `vision_analyze`.

## Wiring

Each module exports a `(ctx, args)` function. Each `src/agent/runtime/tools/builtins/<name>.ts` wrapper calls `defineTool({...})` with description + JSON schema. The builtin registry is auto-generated by `scripts/build-embed-runtime.mjs:generateBuiltinIndex` — dropping a new file in `builtins/` is enough to register it.

After editing TS sources here, run `npm run build:embed-runtime` so `dist/agent-runtime/` (loaded as raw strings into Nodebox by `src/agent/adapter.ts`) picks up the changes.

## When to fall back

The agent should reach for `run_shell node ...` (writing a small inline parser) if:
- The archive uses an unsupported method (ZIP64, LZMA, encryption).
- The PDF returns empty text and is critical.
- A new file type lands that we don't yet have a tool for.

Better to add a real tool here than to leave the agent guessing — these tools exist precisely because asking the LLM to parse binary buffers in `run_shell` loops is wasteful (cf. the directus zip incident).
